# 설계: AIN Store

**상태: 2026-10-31 승인.**

AIN Store는 ainize 앱의 문서 데이터베이스입니다. 문서와 컬렉션, 질의, 실시간 리스너, 보안 규칙, 트리거를 제공하며 백엔드를 따로 짤 필요가 없습니다. 규칙과 트리거는 **AIN 블록체인 합의** 안에서 돕니다. 모든 노드가 모든 쓰기를 규칙에 대고 확인하고, 모든 트리거는 확정된 트랜잭션에서 발동합니다. 운영자를 포함해 누구도 규칙을 건너뛰거나 트리거를 우회하면 드러납니다.

| 구성요소 | 역할 |
| --- | --- |
| AIN 블록체인 | **권한**: 규칙(`.rule`), 트리거(`.function`), 합의로 유지하는 모든 쓰기의 **머클 마운틴 레인지**(상태 O(log n)), DB의 **상태 루트** |
| AinDrive | 해시 주소로 저장하는 **문서 본문과 파일**, **쓰기 기록** |
| Store (프로젝트별) | **SQLite: 유일한 인덱스.** 쓰기 기록과 AinDrive 본문을 재생해 만들고, 조회·질의·실시간을 처리 |
| AIN SSO | 사용자·조직·서비스의 **신원과 역할**, 세션·에이전트·Runs에 대한 위임 |
| ainize Runs | SSO가 발급한 범위 한정 신원으로 **트리거 실행** |

## 원칙

1. **인덱스는 한 번만.** id나 필드로 문서를 찾는 것은 DB의 일이고, SQLite가 이미 합니다. 체인에 그 인덱스를 문서마다 복제하지 않습니다. 체인에는 체인만 줄 수 있는 것을 둡니다.
2. **체인이 모든 쓰기의 순서를 정하고 승인합니다.** 쓰기 하나가 체인의 트랜잭션 하나이고, 합의로 규칙을 검사받으며 트리거를 일으킬 수 있습니다. 체인의 순서가 곧 DB의 순서입니다.
3. **DB는 쓰기 기록의 결정적 함수입니다.** AinDrive의 본문과 함께 쓰기 기록을 재생하면 같은 SQLite가 만들어집니다. 그래서 Store 자체에는 권한이 없습니다.
4. **체인 인덱스는 log₂ n으로 늘어납니다.** 합의가 모든 쓰기를 머클 마운틴 레인지에 접어 넣습니다. 쓰기가 n번이면 봉우리는 최대 ⌊log₂ n⌋ + 1개입니다. 지금까지의 모든 쓰기와 모든 문서의 현재 상태를 O(log n) 경로로 증명할 수 있고, 정리돼 사라지는 것은 없습니다.
5. **처음부터 끝까지 한 신원.** 쓰기에 서명한 SSO 계정이 곧 규칙이 보는 `auth`입니다. 그 쓰기가 일으킨 트리거는 그 계정이나 앱 자신의 계정에서 파생한 권한으로 실행되며, 그보다 넓어지지 않습니다.

## 데이터 모델

```text
체인     /apps/<app>/writes/<collection>/$key            쓰기 슬롯: { id, op, base, h }. 같은 트랜잭션에서 지움
         /apps/<app>/writes/<collection>/.rule           쓰기 규칙 (합의)
         /apps/<app>/writes/<collection>/$key/.function  _storeAppend (native) + 트리거 → ainize Runs
         /apps/<app>/store/mmr                            = { n, peaks: [최대 ⌊log₂ n⌋ + 1개 해시] }   합의로 유지
         /apps/<app>/store/state                          = { upTo, root }   Store가 게시하는 상태 루트
AinDrive <조직 드라이브>/store/<app>/objects/<sha256>     문서 본문(JSON) 또는 파일 바이트
         <조직 드라이브>/store/<app>/writes/<segment>     모든 쓰기 기록, MMR 순서 (잎)
Store    SQLite: documents (collection, id, version, hash, data) + 선언한 인덱스
         (collection, id) → (version, hash) 희소 머클 트리
```

- **쓰기 기록:** `{ id, op: "set" | "merge" | "delete", base: <기준 버전>, h: <본문 해시> }`입니다. 쓰기는 슬롯에 값을 쓰고, 슬롯의 규칙이 검사합니다. 그다음 새 native 함수 `_storeAppend`가 기록을 트랜잭션 해시와 함께 해시해 잎으로 만들고, 앱의 MMR 봉우리에 합친 뒤 슬롯을 지웁니다. 모두 같은 트랜잭션 안에서 일어납니다. 체인에는 `n`과 봉우리만 남습니다. 봉우리 20개로 쓰기 100만 번을, 30개로 10억 번을 덮습니다.
- **왜 MMR인가:** 추가할 때 해시 병합이 O(log n)번이고, 봉우리는 지금까지 쓴 모든 기록을 순서대로 커밋합니다. 기록의 포함 증명은 보관된 잎에서 봉우리까지의 O(log n) 머클 경로입니다. 봉우리를 합의가 계산하므로, Store가 과거 쓰기를 빠뜨리거나, 순서를 바꾸거나, 고치면 체인에 대한 모든 증명이 실패합니다.
- **본문:** sha256을 주소로 AinDrive에 JSON으로 둡니다. 쓰기 기록에는 해시만 있습니다.
- **쓰기 적용:** Store는 확정된 쓰기를 체인 순서대로 따라가며 본문을 가져와 SQLite에 적용합니다. `base`가 문서의 현재 버전과 다른 쓰기는 재생할 때마다 똑같이 거부됩니다. 체인 순서로 결정되는 낙관적 동시성 제어입니다.
- **상태 루트:** SQLite가 현재 문서를 들고, Store는 `(collection, id) → (version, hash)` 희소 머클 트리도 유지합니다. N번의 쓰기나 N분마다 `/apps/<app>/store/state = { upTo: <MMR 위치>, root }` 값 하나를 덮어씁니다. 문서의 현재 상태 증명은 그 루트까지의 O(log n) 경로입니다. 누구나 `upTo`까지의 잎을 재생해 루트를 다시 계산할 수 있고, 모든 잎은 MMR로 증명됩니다.
- **이력:** 잎(쓰기 기록)은 MMR 순서대로 AinDrive에 보관합니다. 잎과 본문이 완전한 원본입니다. Store를 잃으면 여기서 다시 만들고, 다시 만든 루트는 MMR 봉우리와 게시된 상태 루트와 같아야 합니다.
- **비공개 컬렉션:** 쓰기 기록의 문서 id는 조직 키로 만든 HMAC입니다. 본문은 AinDrive 권한 뒤에 있습니다.
- **공개 컬렉션:** 게임 점수나 NFT 메타데이터는 값 자체를 쓰기 기록에 넣고, 다른 앱이 읽을 수 있게 체인에 작은 공개 사본을 둘 수 있습니다.

## 쓰기 경로

```text
SDK ─► Store ─► AinDrive: 본문 저장 → sha256
               └► 체인 tx: SET_VALUE /apps/<app>/writes/<col>/<key> = { id, op, base, h }   (사용자 세션 키로 서명)
                     ├ .rule이 auth(SSO 계정, 조직 역할)와 기록 형태를 확인   — 합의
                     ├ _storeAppend가 MMR 봉우리에 접어 넣고 슬롯을 지움      — 합의
                     ├ .function → ainize Runs (트리거)
                     └ 확정 → Store가 SQLite에 적용 → 실시간 리스너
```

1. SDK는 쓰기를 즉시 로컬에 반영하고 대기 중으로 표시합니다.
2. Store가 본문을 AinDrive에 올립니다. 체인 트랜잭션은 사용자의 **세션 키**로 서명하고, batch는 트랜잭션 하나로 묶습니다.
3. 합의에서 규칙을 검사합니다. 거부되면 클라이언트는 규칙의 오류와 함께 되돌립니다.
4. 쓰기가 확정되면 Store가 적용합니다. `base`가 오래됐으면 클라이언트에 충돌로 알립니다.

**규칙이 검사할 수 있는 것.**
- **합의로 강제:** 누가 쓰는지(SSO 계정, 조직, 역할, 세션 만료), 무엇을 쓰는지(형태, 크기, 허용된 연산), 컬렉션의 한도.
- **재생 시 강제:** "작성자만 수정 가능"처럼 문서의 기존 내용에 달린 조건. 체인에 문서별 상태가 없으므로 이런 규칙은 쓰기를 적용할 때 결정적으로 실행됩니다. 위반은 재생할 때마다 똑같이 거부되고, 누구나 재생해서 확인할 수 있습니다.

## 읽기 경로

- **조회, 질의, 실시간:** 모두 Store의 SQLite가 처리합니다. `where`, `orderBy`, `limit`, 커서, `onSnapshot`. 쓰기 기록으로 최신 상태를 유지하는 유일한 인덱스입니다.
- **검증:** SDK는 어떤 문서든 O(log n) 증명 두 개를 함께 받을 수 있습니다. 하나는 현재 버전이 `/apps/<app>/store/state`의 상태 루트에 들어 있다는 증명이고, 하나는 그 버전을 만든 쓰기가 체인의 MMR에 들어 있다는 증명입니다. 본문 해시도 확인합니다.
- **읽기 권한:** 쓰기 기록에는 내용이 아니라 해시만 있습니다. 본문은 SSO 역할과 공유에 따른 AinDrive 권한으로 보호하고, Store는 질의와 리스너에 컬렉션의 `read` 규칙을 적용합니다.

## AIN SSO로 권한 연결

### 체인 위의 신원

- **계정:** SSO 계정마다 AIN 주소가 있습니다. 사용자가 자기 지갑을 연결하거나, SSO가 계정의 패스키(AIN WebAuthn-P256)에서 주소를 만듭니다.
- **디렉터리:** SSO는 규칙이 필요로 하는 정보를 자기 체인 앱에 게시합니다. 앱에 쓰던 push 모델을 그대로 씁니다.
  - `/apps/ain_sso/orgs/<org>/members/<addr> = "<role>"`
  - `/apps/ain_sso/sessions/<sessionAddr> = { addr, org, exp }`
- **세션:** 로그인하면 수명이 짧은 세션 키(디바이스 위임의 `cnf` 키)가 생기고, SSO가 이를 `sessions/`에 등록합니다. 브라우저가 이 키로 서명하므로 사용자는 체인 키를 다룰 일이 없습니다.
- **수명 주기:** 정지, 퇴사 처리, 세션 폐기는 해당 항목을 지웁니다. 다음 블록부터 그 항목을 확인하는 모든 규칙이 거부합니다.

### 규칙

```text
/apps/<app>/writes/articles/.rule.write:
  getValue('/apps/ain_sso/sessions/' + auth.addr + '/org') === '<orgId>'
  && ['editor','admin'].includes(getValue('/apps/ain_sso/orgs/<orgId>/members/'
       + getValue('/apps/ain_sso/sessions/' + auth.addr + '/addr')))
  && util.isDict(newData) && ['set','merge','delete'].includes(newData.op)
```

SDK는 `role in ['editor','admin']`을 이 형태로 바꿔 주는 도우미를 제공합니다. 규칙은 앱과 함께 리뷰하고 배포합니다.

### 트리거와 ainize Runs

```text
확정된 tx ─► 체인 .function (REST, 화이트리스트 URL) ─► ainize 노드
   노드: tx를 해시로 조회해 확정됐는지, 이 경로를 썼는지 확인          (위조 이벤트 차단)
   노드: 이번 실행을 위한 리소스 범위 위임(ain-rdlg+jwt)을 SSO에 요청
   Run은 그 위임과, /apps/ain_sso/sessions에 등록한 일회용 세션 키로 실행
   Run의 쓰기도 같은 체인 규칙을 통과해야 함
```

- **트리거 선언:** `ainize.json`에 트리거마다 쓸 수 있는 경로와 읽을 수 있는 AinDrive 객체를 선언합니다. 예: `"on-article": { "type": "ain", "path": "/apps/<app>/writes/articles/$key", "as": "app", "writes": ["/apps/<app>/writes/translations"] }`.
- **앱으로 실행 (`as: "app"`):** Run은 조직이 소유한 프로젝트 자신의 SSO 서비스 계정으로 동작합니다. 권한은 선언한 범위이며, 조직이 그 계정에 준 역할을 넘지 않습니다.
- **호출자로 실행 (`as: "caller"`):** Run은 트리거한 트랜잭션에 서명한 계정을 대신해 동작합니다. 그 사용자가 할 수 있는 것 이상은 할 수 없습니다.
- **검증된 이벤트:** 노드는 무엇이든 실행하기 전에 이벤트를 체인에 대고 확인합니다. 트리거별 URL 토큰은 요청 수 제한 용도로만 남깁니다.
- **일회용 키:** Run의 세션 키는 실행 시간 제한과 함께 만료됩니다. 조직의 위임을 폐기하면 그 조직의 Runs도 멈춥니다.
- **스케줄·웹훅 트리거:** 항상 `as: "app"`으로 실행합니다.

## 용량과 비용

체인 상태는 문서 수가 아니라 쓰기 횟수의 log₂로 늘어납니다.


- 쓰기가 n번이면 체인에는 봉우리가 최대 ⌊log₂ n⌋ + 1개 있습니다. 쓰기 100만 번 미만이면 약 4KB, 10억 번이면 약 6KB입니다. 문서마다 항목을 두면 문서 수에 비례해 문서당 약 300B씩 늘어납니다.
- 쓰기 슬롯은 같은 트랜잭션에서 지우므로 쓰기 기록이 체인에 쌓이지 않습니다. 기록 자체(건당 약 100B)는 AinDrive에 저장합니다.
- **앱별 예산**(결정 D2)은 계속 격리 장치입니다.
- **쓰기:** 쓰기나 batch마다 트랜잭션 하나이고, 확정 시점(수 초)에 응답하며 SDK의 대기 상태가 그 시간을 가립니다.
- **읽기**는 체인에 닿지 않습니다.
- **모니터링:** 5분마다 앱별 예산 사용량, 적용 지연(Store의 위치와 MMR `n`의 차이), 보관 완전성(`n`까지의 모든 잎이 AinDrive에 있는지), 상태 루트 지연, 트리거 실패를 확인해 70%, 85%에서 앱 소유자에게 알립니다.

## 기존 데이터 이전

모든 이전은 같은 단계를 따릅니다: 내보내기 → 가져오기 → 병행 운영하며 비교 → 전환 → 실서비스 검증 → 기존 사본 제거. 실서비스를 처음부터 끝까지 검증해야 이전이 끝납니다.

## ainize Runs에 더 필요한 것

"트리거와 ainize Runs" 절의 내용 중 아직 없는 것들입니다.

- 체인의 REST 함수 화이트리스트에 ainize 실행 URL 추가.
- 노드에 ain-js 연결. "체인에 설치"가 503 대신 실제로 동작하게.
- 이벤트를 체인에 대고 검증.
- 실행마다 SSO 리소스 범위 위임 발급과 일회용 세션 키 등록.
- 트리거 선언에 `as`와 `writes` 추가.

지금은 트리거된 Run이 프로젝트를 마지막으로 push한 사람의 키로 실행되며, 이 설계가 그것을 대체합니다.

## 만드는 순서

1. 체인: `_storeAppend` native 함수(MMR 추가와 슬롯 삭제), 앱별 예산, 삭제는 항상 허용, ainize를 REST 화이트리스트에 추가.
2. SSO: 디렉터리 게시(`/apps/ain_sso`의 조직·멤버·세션), 로그인 시 세션 키 발급.
3. Store: SDK, 쓰기 추적과 결정적 적용, SQLite 인덱스, 희소 머클 상태 루트와 증명, AinDrive 본문과 잎 보관, SSE, 규칙 도우미.
4. Runs: 이벤트 검증, 위임, `as`와 `writes`, 체인 설치.
5. 기존 앱 이전: 작은 앱부터, 가장 큰 앱은 병행 운영.

## 결정 (2026-10-31 승인)

- **D1. 체인 인덱스는 O(log n).** 새 native 함수 `_storeAppend`로 합의가 유지하는 모든 쓰기의 머클 마운틴 레인지와 상태 루트. SQLite가 유일한 질의 인덱스이고, AinDrive가 본문과 쓰기 기록을 담습니다. 메인넷 합의 변경입니다.
- **D2. 공용 무료 풀 대신 거버넌스로 정하는 앱별 상태 예산, 삭제는 항상 허용.** 메인넷 합의 변경입니다.
- **D3. SSO가 조직·멤버·세션을 체인에 게시하고, 사용자는 SSO가 발급한 세션 키로 서명.**
- **D4. Runs는 `as: "app"`(기본) 또는 `as: "caller"`로 실행하고, SSO 리소스 위임으로 선언한 경로에 한정.**
- **D5. 데이터에 달린 규칙은 기본적으로 결정적 재생에서 실행. 이후 선택지: 트랜잭션에 문서의 O(log n) 상태 증명을 실어 합의에서 검증.**
